# Agent adapter architecture: concepts

This document explains the mental model behind Sortie's agent adapters: how a coding-agent runtime becomes a `kind` string the orchestrator can dispatch to, the boundaries an adapter package must respect, the test gate that keeps a runtime's integration suite honest, what the per-adapter notes file is for, and how a runtime's support for the Agent Client Protocol is qualified rather than assumed. Read [Add or refresh an agent adapter](agent-adapter-howto.md) for the ordered procedure that applies these ideas.

Seven packages under `internal/agent` implement `domain.AgentAdapter` today: `claude`, `clientprotocol`, `codex`, `copilot`, `kiro`, `mock`, and `opencode`, registering the kinds `claude-code`, `agent-client-protocol`, `codex`, `copilot-cli`, `kiro`, `mock`, and `opencode` respectively. That count comes from the `var _ domain.AgentAdapter = (*X)(nil)` compile-time assertion each package carries; grep for it rather than trusting a number written down elsewhere, including this sentence once another adapter lands.

## The kind registry and the composition root

`internal/registry` defines `Registry[T, M]`, a generic map from a `kind` string to a constructor function `T` plus declared metadata `M`. `registry.Agents` is the instantiation for agent adapters: `NewRegistry[AgentConstructor, AgentMeta]("agent")`. An adapter package associates its kind string with its constructor by calling `registry.Agents.Register` or `registry.Agents.RegisterWithMeta` inside an `init()` function. Registration panics on an empty kind or a duplicate, because both are programming errors caught the moment the binary starts, not runtime input to validate.

Calling `init()` requires the package to be imported somewhere. `cmd/sortie` is the composition root: it blank-imports every kind package purely to trigger that side effect, then resolves the operator's configured `agent.kind` through `registry.Agents.Get(kind)` and constructs the adapter there. No other package in the tree imports an adapter package by name for this purpose. The orchestrator that later drives that adapter through `StartSession`, `RunTurn`, and `StopSession` never learns which package produced it; it holds only the `domain.AgentAdapter` interface value `cmd/sortie` handed it.

This split is what makes adding a runtime additive: the orchestrator's dispatch logic does not change when a new kind is added, because it was never written against a specific kind to begin with.

### Why importing a registering package from core is a layering violation

`go build` does not enforce any of this. A file under `internal/orchestrator` can import `internal/agent/kiro` directly, call its exported constructor, and compile cleanly. Doing so defeats the point of the registry: the orchestrator would then depend on a specific runtime's package, and swapping or removing that runtime would touch orchestrator code instead of staying inside `cmd/sortie`'s wiring.

`internal/adaptertest/contract_test.go` is what actually stops this. Its core-import rule walks every non-test file under `internal/orchestrator` and rejects an import path under `internal/tracker`, `internal/scm`, `internal/agent`, or `internal/notify` unless that path names one of a small set of shared, kind-less helper packages (below). The rejection reason differs by what the import does:

- An ordinary import of an adapter package is rejected because "the orchestrator resolves an adapter kind through the registry rather than importing its package".
- A blank import outside a test file is rejected because "`cmd/sortie` owns the blank imports that trigger kind registration". Only `cmd/sortie` may blank-import a kind package.
- An import of a package whose non-test files pull in `testing` (a test-support package) is rejected outright, because production code must never depend on test-only code.

The same file also enforces the mirror rule for adapter packages themselves: one adapter package must not import another adapter package, and no adapter package may import `internal/orchestrator` at all. A shared package under a family root (a tracker, SCM, agent, or notifier family) is importable by its siblings only when it is named in that file's own registry of kind-less shared packages; anything else is exempt only within its own subtree.

## Adapter boundary rules

An adapter package owns exactly one kind's protocol translation and nothing else:

- **No cross-adapter imports.** `internal/agent/kiro` cannot import `internal/agent/codex`, and neither can import the orchestrator. A behavior two adapters need is a shared helper, not a cross-import.
- **Normalize external responses to domain types at the boundary.** An adapter's exported surface speaks only `domain` types: `domain.AgentAdapter`, `domain.Session`, `domain.TurnResult`, `domain.AgentEvent`, `domain.AgentError`. Whatever shape the underlying CLI or protocol actually emits, whether newline-delimited JSON, a JSON-RPC frame, or a plain-text transcript, is parsed and translated to those types before it leaves the adapter package. Nothing downstream ever branches on a vendor-specific field or string.
- **Shared helpers live in a package named for the concern they serve, never duplicated per adapter and never in `internal/domain`.** `internal/agent/agentcore` holds shared session, event, and disposition logic; `internal/agent/procutil` holds subprocess group handling; `internal/agent/mcpconfig` holds MCP configuration parsing; `internal/agent/sshutil` holds SSH invocation helpers; `internal/agent/jsonrpc` holds newline-delimited JSON-RPC framing for a kind whose protocol needs persistent framing. `internal/adaptertest/contract_test.go` declares each of these importable by any package under the agent family root and by the orchestrator's own production code, precisely because none of them registers a kind or holds an adapter. Logic that is genuinely scoped to one runtime nests inside that runtime's own package instead of migrating outward.
- **Test-only shared helpers are importable by adapters but not by production code.** `internal/agent/agenttest` (and its `dispositiontest` subpackage) hold conformance assertions such as `agenttest.AssertMCPInjection`, `agenttest.AssertUsageContract`, `agenttest.AssertMeasurementAbsent`, and `agenttest.AssertUsageReporting`, used by every adapter's own test suite. Their non-test files import `testing`, so `internal/adaptertest/contract_test.go` bans them from any production file, orchestrator or adapter, while still allowing an adapter's `_test.go` files to import them.

## Declaring an adapter's properties to the orchestrator

Beyond the constructor, `registry.AgentMeta` lets an adapter declare properties the preflight pipeline and dispatch path need without inspecting the adapter itself: `RequiresCommand` (whether `agent.command` must be non-empty), `ValidateAgentConfig` (an adapter-specific config validator returning `[]registry.ValidationDiag`), `MCPInjection` (what the adapter does with the worker-generated MCP configuration path: `Supported`, `Translated`, or `Unsupported`), `SessionResumeBlockedBy` (a pure function reporting which of the adapter's own config keys, under a given passthrough map, would prevent session resume across separate process launches), and `UsageArrival` / `UsageAttribution` / `UsageSessionRules` (when a `token_usage` event becomes available, what it attributes to, and the per-session rule set that narrows the pair when a passthrough setting or the launch mode changes what the runtime reports). A kind registered with the bare `Register` call carries the zero value of `AgentMeta`, which is read as "no special requirements" rather than an error.

## The per-adapter integration-test gate

Each adapter package with a live-runtime integration test gates it behind its own `SORTIE_<ADAPTER>_TEST=1` environment variable, one gate per package. When the variable is absent or not `1`, the test calls `t.Skip` and reports skipped, never failed and never silently treated as passed. There is no per-operation gate inside a package and no read-only carve-out: a package gets exactly one gate that turns its entire live-runtime suite on or off. Credentials or model identifiers the suite also needs arrive through their own adapter-specific variables (for example an API key or a command path), which are meaningless without the package's own gate set and are never treated as gates themselves.

## Adapter notes files

`docs/<kind>-adapter-notes.md` are working notes for the next person changing that adapter, not release documentation and not an implementation history. Each one exists to answer the question a maintainer asks right before touching the code: what does this runtime actually do, where does it disagree with its own documentation, and what already went wrong here.

What belongs: the runtime fact that most other behavior follows from, how to recover a volatile detail (a flag surface, a model list) from the installed binary rather than from prose, exit-code and output quirks the adapter works around, and anything measured against the live binary that contradicts the vendor's own documentation.

What does not belong: a changelog of what this file used to say, a pinned binary version (the adapter reads its own version from the runtime's handshake or output when one is available; the notes prose does not carry it), a restatement of the upstream project's own documentation, a leading blockquote, or hard-wrapped prose. A notes file is prose to be read now, not a record of how it came to be.

## Qualifying a runtime's protocol support

`internal/agent/clientprotocol` reaches a runtime through a single generic kind, `agent-client-protocol`, configured by `agent.command` like any other kind. Because one operator build of that adapter can drive many different underlying agent binaries, and because a binary's advertised protocol capability can be wrong, `internal/qualification` exists to measure a runtime's actual behavior rather than trust its self-report.

The package works from a fixed, runtime-neutral vocabulary. A `Surface` is one channel a runtime can be driven through: `protocol` (the Agent Client Protocol itself), `native_json` or `native_stream_json` (a runtime's own structured output, when it has one), or `aggregate` (a property that spans surfaces, such as workspace containment). A `Capability` is one of ten load-bearing properties the orchestrator's decisions actually depend on: turn disposition, retry classification, token ceiling, tool-server delivery, session continuation, permission handling, runtime identity, workspace security, process cleanup, and eligibility. A `Case` is one scenario within a capability (success, cancellation, a runtime refusal, and so on). A `Grade` states what one surface-capability pair's measurement found: `usable`, `gap`, `corroboration_only`, `not_observed`, `declared_gap` (the operator asserted the runtime cannot produce this case), `not_inducible` (no input can force this case at all), or `unmeasured`. Deliberately, there is no manual override grade: an unmeasured row is reported as unmeasured, never silently treated as a pass.

A live run produces a set of `qualification.Record` rows, one piece of evidence each, tagged with its scenario, surface, capability, source channel, and grade. `qualification.ExplainEligibility` folds those rows into an `EligibilityReport`. For four capabilities where the protocol surface is compared directly against a native reference (turn disposition, retry classification, token ceiling, and session continuation), it derives a baseline grade per surface with `DeriveBaselineGrade`, computes the richest grade across the runtime's structured native surfaces as the reference, and compares the protocol surface's grade against it: a protocol grade at or above the reference stands `satisfied`, a protocol grade below it stands `below`, and a missing or unmeasured baseline stands `unmeasured`. The remaining capabilities each contribute their own singleton row instead of a comparison. The aggregate `Verdict` is `not_qualified` if any row stands `below`, `unmeasured` if none stand `below` but at least one stands `unmeasured`, and `qualified` only when every row is `satisfied`. This is the mechanized form of the rule that decides whether a runtime should be driven over the protocol or kept on its native surface: protocol routing wins only when it loses nothing on any capability the orchestrator's decisions actually depend on, and an unmeasured capability never counts as a win by default.

The operator's own input to a live run is a `qualification.RuntimeProfile` document: a JSON file naming the runtime's identity tokens, its adapter notes and measurement artifact paths, a sample published workflow route, the argument vector for each measured surface's entry point (`EntryPoint`), how to recognize a terminal outcome in each structured surface's own output (`Recognizer`), and the runtime's declared gaps and declared absent surfaces. `internal/qualification/profiles/` holds one tracked profile document per qualified runtime, named by the runtime's own id (`profiles/gemini-cli.json`, for example). `RuntimeProfile` is decoded strictly: an unknown or missing member at any level is rejected, as is a declared case outside its capability's own set or a declared gap whose paired case is not declared alongside it. `qualification.DecodeRuntimeProfile` decodes a profile from bytes; `qualification.ReadRuntimeProfileFile` additionally resolves the paths the profile names, relative to the nearest ancestor directory holding `go.mod`, so the result does not depend on the caller's own working directory. `internal/qualification/probe` drives the live run itself: it resolves the operator's coordinates (a runtime binary path, a model identifier, authentication variable names, and the profile document to measure against) and gates the run behind its own environment variable, following the same one-gate-per-package convention as an adapter's integration test.

The adapter notes document a qualified run produces is not free-form prose about grades. It MUST carry a fixed sequence of headings (`qualification.NotesSections`), exactly one `Eligibility:` line matching the run's verdict, and one status-labeled row per measured surface-capability pair using the exact label `qualification.StatusLabel` maps to that pair's grade. `qualification.ValidateNotes` checks a candidate document against a `NotesExpectation` and rejects a mismatch, a missing row, an extra row, or a row whose label does not match its own claimed grade. This is what keeps a hand-written notes document from drifting away from what a run actually measured.
