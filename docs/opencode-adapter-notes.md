# OpenCode adapter notes

Working notes for anyone changing Sortie's OpenCode adapter in `internal/agent/opencode`: why this one does not use the shared subprocess skeleton, where OpenCode's session and permission model collide with ours, the launch contract the adapter drives, and the failures that look like something else.

Last updated: 2026-10-09

## Where to get the volatile facts

Nothing here pins a flag list, an event vocabulary, a permission key set, or an exit code. Read the argument surface off `opencode run --help` on the version you are targeting, take the permission actions, provider configuration, and server surface from the rendered docs at `opencode.ai`, and go to the upstream repository when the docs and the shipped binary disagree, which for this CLI they routinely do. The adapter's `command.go` and `parse.go` define what Sortie actually sends and reads.

## The surface we drive, and what it is not

`opencode run` is a thin client over the same HTTP and event APIs the server mode exposes. Without an attach target it boots a server in-process and talks to it through an internal fetch. That is the single most useful thing to know about this integration, because it explains every gap in the stdout stream: the JSON that `run` prints is a CLI-specific projection of selected server events, not the canonical event bus. It carries no session-started envelope, no status or idle transition, no permission event, and no final result envelope. Process exit is the only explicit end-of-turn signal on this surface.

If a future change needs anything the projection hides, retry and backoff state above all, the answer is the server surface with its documented schemas, not a richer parse of `run` output.

One trap to carry into that work if it ever happens: nothing in this adapter wires a port today, but the underlying server mode treats a port value of zero as a sentinel rather than as "pick any free port", and reading that wrong in either direction either attaches to a server this process did not start or misses the server the CLI actually opened. Confirm the current sentinel semantics against `opencode run --help` and the server-mode docs at `opencode.ai` before trusting a zero default, and set the port explicitly on both sides regardless of what you find there.

## Version check and launch contract

`StartSession` runs the configured command with `--version` before any turn, parses whichever line of output first carries a bare semantic version, and accepts only a leading number of 2. Any other leading number, or output with no readable version at all, refuses the session outright rather than guessing; the version query is bounded the same way any other auxiliary launch is, and it runs at every session start without being cached. The refusal names the installed version and the package, `@opencode/cli`, because another npm package installs the same `opencode` command, and a bare "install OpenCode" sends an operator back to the wrong one.

Two settings are refused before any launch, each with a message naming the setting: `opencode.pure`, which the runtime has no switch for, and `opencode.effort` or `opencode.variant` without a plain `opencode.model`, because the runtime reads a variant only as a `#` suffix on the model.

The launch contract has four parts worth knowing:

- The runtime trusts `PWD` ahead of its own working directory, so the adapter's shared workspace-binding helper sets `PWD` to the verified workspace path on every local launch. A workspace removed between the pre-launch check and the runtime's own directory change fails the turn with the runtime's own text, not a Sortie diagnostic.
- The runtime reads the prompt from standard input: giving it a positional prompt after `--` sends it to the model twice, so the adapter never does that.
- One inline configuration document, delivered through `OPENCODE_CONFIG_CONTENT`, carries the tool policy, the sharing setting, the compaction setting, and the tool-server declarations; a malformed document is dropped whole rather than partially applied, silently, so a marshaling bug on this side fails open rather than loud.
- The launch always adds `--standalone`, which keeps the runtime's private per-launch server from touching any other client's session: the alternative, the shared background service, keeps the environment and configuration of whichever client started it first and outlives Sortie, so the adapter never launches without that flag.

The runtime imports sessions stored by earlier releases into its own store in the background of every launch, unordered with respect to the turn that launch runs, so resuming a session the import has not reached yet fails the turn outright rather than waiting; the failure recovers on its own once a later launch's import catches up. A completely fresh data root the runtime has never initialized has its own one-time race: the first launch against it wins a schema-creation lock and every concurrent launch against the same root loses and exits early, indistinguishable at the adapter's boundary from any other early exit, and self-resolving on retry once the schema exists.

## Why this adapter owns its own loop

Every other fork-per-turn adapter delegates the subprocess lifecycle to `agentcore.ForkPerTurnSession`. This one does not. It starts the process itself, runs its own stdout reader goroutine, its own wait goroutine, and its own select loop, because it needs two things the skeleton does not offer: a deadline on the first JSON event rather than on the turn, and a post-exit subprocess query against the same binary to recover usage.

That independence is a maintenance hazard. Improvements to the shared skeleton do not reach this adapter, so when the two are meant to behave alike, they have to be kept alike by hand. The terminal decision itself is still shared: evidence is assembled here and handed to `agentcore.FinalizeTurn`, so disposition and error kinds stay consistent across the fleet.

The first-JSON deadline defaults to thirty seconds and is overridden by the workflow's read timeout. It stops once the first envelope arrives, so it guards a subprocess that never starts talking, not a mid-turn stall. Stalls are the orchestrator's business.

The adapter owns both pipe read ends for the turn's lifetime, so the reap runs independently of the stdout reader: reaping the process no longer closes either read end, and the reader keeps draining whatever the process wrote regardless of when the reap happens. The stderr bound inside the wait goroutine no longer protects the reap, which now happens ahead of it: the wait goroutine reaps first and applies the bound afterwards, so a descendant holding the stderr handle can no longer withhold the reap at all. What the bound protects now is the publication of the turn's result, which waits behind it, and the permission-refusal warning the finalize path reads; firing it costs that warning on the residual path where reaping the process does not also release the collector. The delay it can add is why nothing that must react to the subprocess being gone reads the result channel: the reader's own bound is armed from the reap instead. The four early-return arms bound their own drain of the stdout reader rather than waiting on it unconditionally, so a descendant that inherits only the stdout handle cannot withhold any of them past that same bound.

## Session identity and the dir-scoped resume

A session ID is server-generated and learned from the first envelope that carries one. The adapter adopts it, and a later envelope carrying a different ID is treated as a fault that fails the turn rather than a thing to reconcile.

Resume is scoped to the directory the session was created in. Resuming a valid session ID from a different project directory does not error: the process exits zero and prints nothing. Downstream that becomes the early-exit report, exit status 0 with no standard-error output, which reads like the runtime never responded rather than like a resume that never matched. The adapter satisfies the constraint by construction: the issue workspace reaches every turn as the process working directory, with `PWD` set to the same path on a local launch, so the two cannot diverge. The trap is in tests: a resume test that runs the second turn in a fresh temporary directory passes through the code path without exercising resume at all. Share the workspace across both turns or the test proves nothing.

Sessions are persisted in one global database under the user's home directory, not in a per-project store inside the workspace. Isolation between concurrent issues comes from distinct server-generated IDs, not from separate storage, and removing a workspace reclaims none of it.

## Permissions

OpenCode's permission control is config-driven rather than flag-driven: each key resolves to allow, ask, or deny, through an ordered list of rules where the last rule matching a tool's action and resource wins, defaulting to ask when nothing matches. The adapter injects its policy through the inline configuration document; the critical detail is that OpenCode deep-merges that value into the permission rules it already resolved from every other configuration source rather than replacing them, the adapter's own document loading last. An inherited value from the operator's shell would therefore bleed into the merged result. The adapter scrubs every variable it manages out of the inherited environment before appending its own, so an operator-side value never survives into the subprocess. Keep that scrub in step with the managed set: a new managed variable that is not also scrubbed is a leak. A live check that reads this merge back reads the runtime's own resolved configuration (its private-server API, since its debug listing only lists configuration sources rather than the merged document) rather than running a model turn to observe the effect indirectly, so it needs no credential and is not exposed to a provider's own admission rules.

The policy the adapter emits is closed rather than open. When the workflow names allowed tools, every other permission key the adapter knows about is denied explicitly, which is why that set exists at all. It is a policy input, not a validation whitelist: the runtime accepts more keys than its documentation lists, including a catchall for keys nobody has enumerated, so a key the workflow names is forwarded verbatim whether or not the adapter recognizes it, with unknown keys logged at debug level. Rejecting an unrecognized key would break configurations OpenCode itself accepts. The closed set includes the runtime's own built-in actions beyond the documented keys, and every documented key is forwarded unchanged, letting the runtime's own renames apply.

Separately from the policy, the adapter runs with permission prompting bypassed by default, because the alternative is the runtime refusing every permissioned tool call instead of performing it and ending the turn at the first refusal rather than merely reporting it. Validation warns when a workflow turns that off, and treats an overlap between the allowed and denied lists as an error, since the two would contradict each other.

A refusal surfaces on stderr as a human-readable warning line, styled with escape sequences, while stdout stays JSON-clean. The adapter strips those sequences before checking the line's prefix; skip that step and the check never matches real output. The adapter recognizes the notice from the collected stderr after the process exits and routes it through `agentcore.DecideHumanRequest` like every other adapter. Recognizing it at turn end rather than as it happens means the notice arrives late and does not reset the first-JSON timer, neither of which matters while the warning never reaches stdout.

OpenCode's hosted free-tier model refuses any request whose tool set lacks its shell tool or its read tool, and that refusal reaches this adapter as a run-level error rather than as the permission-refusal notice above. When the session's own tool policy is what denied one or both of those tools, the adapter appends a clause naming the denied tool to the vendor's own refusal text; a refusal from a model that is not free-tier limited, or from tool settings that do not touch either required tool, gets no such clause. The recognition depends on the vendor's current wording; a rewording upstream calls for a one-key-at-a-time re-measurement of the fixtures this check is built from, not a broadened text match.

## Usage accounting

Step-scoped token counts on the stream are not a running total. Between the tool step and the final text step of one turn the numbers move in both directions, so summing them across steps is wrong and taking the last one is wrong too.

The registered kind declares `turn_end` arrival and `per_model` attribution: the figure `queryExportUsage` recovers after the subprocess exits is reported through the shared turn-end report in `agentcore`, carrying the model of the last kept export message. The export runs over SSH in remote mode too, so the disposition does not change with the launch mode, unlike `copilot-cli`.

The adapter recovers authoritative usage by running a sanitized session export after the subprocess exits, and it computes its own totals from per-message figures rather than reading the export's session aggregate. Two reasons, both durable. The aggregate spans the entire session including turns from an earlier run, while the figure Sortie reports is run-scoped; and the aggregate's own total field is not the sum of its input and output components, because it also folds in cache and reasoning tokens. So the adapter selects assistant messages by session ID and, on a resumed session, by creation time at or after the run's start, then sums them. It counts a message only once its step has finished, which the message's `finish` field marks: the runtime saves an assistant message with all-zero tokens before calling the model and fills them in when the step finishes, so a turn killed mid-step exports a placeholder that is not a measurement. The export is sanitized deliberately, so tool output bodies never reach a log. The configuration document the adapter writes disables the runtime's title agent, because the title request the runtime would otherwise make is billed and recorded in no message the per-message sum reads.

A failed or empty export must never lower a figure the run has already reported. The finalize path skips the update entirely rather than replacing a settled value with zero.

## Failure detection

An error envelope on stdout is the authoritative failure signal. The process exit code is not load-bearing and has changed meaning across releases; do not key anything on it.

The error envelope carries `type`, `message`, and a numeric `status` when present as flat members.

One failure can arrive as two error envelopes: the actionable diagnostic the session publishes, and a generic placeholder the run command reports when the underlying fault was not in its API error schema. Their order on the stream is not guaranteed, so the adapter keeps whichever envelope carries detail rather than whichever arrives last. When only the placeholder was seen, it reaches the operator as it is, so a report of the generic message is a signal to reproduce, not a bug in the parse.

Work evidence for the turn is this turn's own parsed assistant parts, text, reasoning, or tool use, never the export figure, which is non-zero on any turn after the first. An exit-zero run that parsed envelopes but produced no assistant output takes the shared zero-work row and is reported as a failure rather than a silent success.

## Sortie's own tools

`StartSession` parses the worker-generated MCP configuration and translates it into OpenCode's own server entries, additive to whatever an operator's own project or global configuration already declares, never as the generated file's path handed over verbatim; live probing found the runtime rejects that standard `mcpServers` key outright. The entries ride under the `mcp` key of the inline configuration document. A turn's document reaches the runtime by one of two routes: the turn's own environment build on a local launch, and the SSH carrier's settings on a remote launch. It is never set in the shared managed-environment builder, so the session export and session delete auxiliary invocations that builder also serves never carry it, on either launch, and never spawn a tool sidecar of their own.

Tool servers reach a local launch only. An SSH turn carries the same document on the SSH carrier without the `mcp` member, so a remote session runs without tools. The carrier is in use on a remote launch for the managed settings and for any variable the launch carries, and the document rides it as one more setting.

The run projection this adapter reads carries no MCP startup-status signal: see "The surface we drive, and what it is not" above for the event types it omits. A server that fails to start is visible only indirectly, as the agent's own tool calls failing, not as a distinct diagnostic on this surface. The runtime forks each configured server's start in the background while it prepares the session, awaiting neither the spawn nor the connection before the turn proceeds. Every tool-server call the model makes is reported to Sortie under one runtime-chosen name rather than the tool's own name, because the runtime's code-mode execution path is the only route to a tool server and the adapter reads whatever name the runtime reports.

## Verifying a change

Unit tests cover argument and environment construction, the permission policy, event parsing, export parsing, and disposition. The tests that drive the real binary are env-gated on `SORTIE_OPENCODE_TEST=1` and skip cleanly without it; keep them skipping cleanly rather than failing. `SORTIE_OPENCODE_COMMAND` points at a specific binary and `SORTIE_OPENCODE_MODEL` overrides the model. `SORTIE_OPENCODE_CREDENTIAL_ENV` names the variables the credential-verification suite's refused-credential case overrides; its absence skips only that one case, cleanly, with a logged reason, and the case accepts either `credential_unverified` or the early-exit report as the outcome. The gated suite also runs the configured command with `--sortie-unknown-switch` appended on a verification request and on a working session, proving each ends with the early-exit report; a runtime that accepts the switch skips the case with a logged reason naming it. Give the suite a generous read timeout: a first launch on a clean machine runs database migrations that can take well over the default before the first event appears. And any test that resumes a session must run both turns in the same workspace.

`TestIntegration_ScriptedModel` runs under the same gate, needs no credential and spends nothing. It launches the binary against a loopback endpoint that answers from a fixed script. The runtime reaches the endpoint through a provider document the test writes into the isolated home and names in `OPENCODE_CONFIG`, because the adapter owns `OPENCODE_CONFIG_CONTENT` and drops any value it inherits; the document takes its key from an `{env:}` reference, since the runtime does not read the provider's key variable on its own, and that variable carries a sentinel value. The case asserts five properties: the turn ends completed, the reported usage equals everything the endpoint served field by field, the scripted read reaches one normalized tool result carrying the file's content, the sentinel appears only in a credential header, and a request beyond the script ends the turn failed with the endpoint's message. It isolates `HOME` and the XDG base directories, so a command reached through a version-manager shim that reads `HOME` fails to start; name the binary by an absolute path whose interpreter resolves without `HOME`. The working-credential case asserts that its verification turn reports measured, positive usage.
