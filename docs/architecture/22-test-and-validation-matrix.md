## 17. Test and Validation Matrix

Sortie's tests cover the behaviors defined in this architecture document.

Validation profiles:

- `Core Conformance`: deterministic tests required for all core features.
- `Extension Conformance`: required only for optional features that are implemented.
- `Real Integration Profile`: environment-dependent smoke/integration checks recommended before production use.

Unless otherwise noted, Sections 17.1 through 17.7 are `Core Conformance`. Bullets that begin with `If ... is implemented` are `Extension Conformance`.

### 17.1 Workflow and Config Parsing

- Workflow file path precedence:
  - explicit runtime path is used when provided
  - cwd default is `WORKFLOW.md` when no explicit runtime path is provided
- Workflow file changes are detected and trigger re-read/re-apply without restart
- Invalid workflow reload keeps last known good effective configuration and emits an operator-visible error
- Missing `WORKFLOW.md` returns typed error
- Invalid YAML front matter returns typed error
- Front matter non-map returns typed error
- Config defaults apply when optional values are missing
- `tracker.kind` validation enforces registered tracker adapters
- `tracker.api_key` works (including `$VAR` indirection)
- `$VAR` resolution works for tracker API key and path values
- `~` path expansion works
- `agent.command` is preserved as a whitespace-delimited argument-vector string in the string form and, element by element with no splitting, in the list form; `SORTIE_AGENT_COMMAND` sets the string form and replaces a list the file holds
- A non-positive `agent.turn_timeout_ms` is rejected at config parse time; an absent key takes the default
- An absent `agent.max_consecutive_absences` key takes the default of `3`; `0` and negative values are rejected at config parse time; `SORTIE_AGENT_MAX_CONSECUTIVE_ABSENCES` overrides a file-supplied value and is rejected under the same rule
- An absent `reactions.ci_failure.watch_window_ms` key takes the default; a negative value and a value above `9223372036854` are rejected at config parse time, naming the field and the value; `9223372036854` itself is accepted
- Per-state concurrency override map normalizes state names, rejects an entry outside the integer range, and ignores other invalid values
- A string-typed adapter configuration key whose value carries another YAML type is rejected with a diagnostic naming the key and the type found, distinct from the absent-key diagnostic, by the earliest surface that reads it: config load for a key the config layer owns, adapter construction and `sortie validate` for a key the adapter owns
- A static check fails when a tracker, source-control, agent, notifier, or config-layer package gains a new discarded string type assertion outside its allowlisted sites
- An integer setting outside the integer range is rejected with a diagnostic naming the setting and the range, for a numeral beyond the signed 64-bit range, a numeral beyond the unsigned 64-bit range, and a negative numeral beyond the range in a setting whose non-positive values are otherwise ignored or defaulted; the range test holds at the exact 64-bit boundaries of either sign and, through the conversion parameterized by integer width, at the 32-bit boundaries; an in-range, non-numeric, or fractional value keeps its existing diagnostic
- Prompt template renders `issue`, `attempt`, and `run`
- Prompt rendering fails on unknown variables (strict mode)
- An `agent.command` that is an empty list, or holds a non-string element, an empty element, or a whitespace-only element zero, fails to load at startup, in `sortie validate` (check `config.agent.command` or `config.agent.command[<i>]`), and on reload, which keeps the previous configuration; a list of strings draws no `type_mismatch` warning
- An empty `tracker.terminal_states` for a tracker kind that derives state from labels, and a blank entry in `tracker.active_states` or `tracker.terminal_states` for any kind, fail to load at startup, in `sortie validate` (check `config.tracker.terminal_states` or `config.tracker.active_states[<i>]`), and on reload, which keeps the previous configuration; an empty `tracker.active_states` loads and draws the `tracker.active_states.empty` warning
- A workflow written for a retired kind loads converted: `agent.kind` and each rule's `agent` name the replacement kind, the retired kind's settings block is gone, the replacement kind's block is present, and one conversion record lists each converted reference in order
- A workflow naming the replacement kind directly, with or without a leftover retired-kind block, is not converted, draws no `agent.kind.retired` advisory, and holds no conversion record
- A kind registered as a live adapter is never converted, whatever the retired-kind registry holds: the workflow runs on the live kind unchanged, holds no conversion record, and draws only the deprecation advisory
- Chain validation rejects, each with its field and message and the first fault in the stated order, a `next` that is not a string, is empty or white space, is on an unnamed rule, names no rule, names its own rule, names a rule without a stage label, or closes a loop (the path identical across runs), a `dispatch.max_consecutive_hops` that is not an integer, is not positive, or is below the longest chain's hops, and a `next` with `tracker.handoff_state` unset; a reload that introduces any of them keeps the previous configuration; `sortie validate` reports each and a short `agent.max_sessions` as a warning; `next` alone is not rule content, and `next` under `match` or `dispatch.default` is an unknown key
- `stage` is present on the first turn, the seeded first turn, continuation turns, and per-rule templates; a template that references `.stage.previous` never fails under strict mode; template analysis accepts `.stage.current`, `.stage.previous`, and `.stage.previous_outcome` and rejects any other `stage` key
- A `match.title` key that is null, bare, or an empty list, a value that is not text or a list, a list element that is not text (with the quoting hint chosen by the value's shape), and a phrase that is empty or only white space each fail the load with the field and message the validation reference lists, from the config builder and through `sortie validate` (check `config.<field>`, exit status 1), and only the first fault is reported, after any fault in the other match keys; a workflow with `match.title` draws no `unknown_sub_key` warning from front-matter static analysis, an unrecognized match key still does, and the static analysis and the builder accept one match-key set; a workflow without `match.title` loads, validates, and routes exactly as before
- Partials: an absolute entry, a `~`-prefixed entry, an entry that leaves the tree, and a symlink that points outside it each fail the load; an expansion drops dot files and loads a file once, in first-seen order, in a workflow directory whose path holds a glob metacharacter; a name with two sources, the reserved name `prompt`, text outside a define block, and a call to an undefined name, also one reached through a branch no data takes, each fail the load; each fault and each render error inside a partial names the partial and the line within it; a failed reload keeps the previous configuration and templates, and a repaired partial applies at the next load

### 17.2 Workspace Manager and Safety

- Deterministic workspace path per issue identifier
- Missing workspace directory is created
- Existing workspace directory is reused
- Existing non-directory path at workspace location is handled safely (replace or fail per implementation policy)
- Optional workspace population/synchronization errors are surfaced
- `after_create` hook runs only on new workspace creation
- `before_run` hook runs before each attempt and failure/timeouts abort the current attempt
- `after_run` hook runs after each attempt and failure/timeouts are logged and ignored
- `before_remove` hook runs on cleanup and failures/timeouts are ignored
- Workspace path sanitization and root containment invariants are enforced before agent launch
- Agent launch uses the per-issue workspace path as cwd and rejects out-of-root paths
- A workspace directory swapped for a symbolic link after preparation refuses every `.sortie` write, read, and removal for that workspace and leaves the link's target unchanged
- Every workspace launch, including a per-turn or auxiliary one, refuses a linked workspace path and starts no subprocess
- Hook environment variables (`SORTIE_ISSUE_ID`, `SORTIE_ISSUE_IDENTIFIER`, `SORTIE_WORKSPACE`, `SORTIE_ATTEMPT`) are set correctly
- The periodic sweep excludes workspace keys held by running entries and scheduled retries, and keys held by a pending reaction entry whose kind pins its workspace, while a non-pinning kind leaves its key a candidate
- Within one sweep pass the terminal check runs before the age bound, and a key removed by the terminal check is not re-evaluated by the age bound
- The age bound removes a workspace whose latest recorded activity precedes the retention window, anchoring on the later of the recorded completion and the recorded push
- A workspace with no parseable activity timestamp is retained regardless of age
- A retention value of `0` or below the floor disables the age bound; a value between `1` and the floor is rejected at config parse time
- A failed tracker state read still lets the age bound evaluate and remove eligible workspaces on that pass
- One sweep summary record is emitted per pass that produced a candidate set, including a pass that removed nothing, and its outcome counters sum to the candidate count
- On Windows, the subprocess of a hook, the reaction triage command, an agent session or turn, an auxiliary launch, or a self-review verification command is a Job Object member before it executes whenever the Job Object was created and assigned; a creation or assignment failure is reported and the launch runs without one
- On Windows, a subprocess of any of those launches whose context is done when its resume is reached never executes; a hook, the reaction triage command, or a self-review verification command past its deadline is reported as timed out, an agent session or turn as cancelled, as is a session start whose version check found the session's own context ended, and any other failure carries the context's error as its cause; one that cannot be resumed is reported as a start failure, whatever deadline expires during the resume call or the teardown after it
- An auxiliary one-shot launch whose output handle a surviving descendant holds returns within its bound with its exit status deciding the outcome
- A hook, the reaction triage command, or a self-review verification command that exits zero while a process it started holds its output is reported as succeeding, on every platform, and no process of its process group, or of its Job Object on Windows, remains when it returns: the termination resends until no process of the group or job is still alive or a 2-second bound elapses, on every platform; a Windows launch running without a Job Object, because one could not be created or assigned, has only its direct process reached by that teardown, and a termination that cannot confirm the tree torn down, on either platform, is reported as a warning instead
- A teardown acts only on the launch it belongs to, for every launch kind this section lists (a hook, the reaction triage command, an agent session or turn, an auxiliary launch, a self-review verification command): tearing a launch down through its reap, its force-termination, its graceful and forced cancellation, and a stop requested after it exited leaves running every process of another launch that holds the same process identifier. On Windows, two launches whose direct children share one process identifier each hold a distinct Job Object with a running member, and tearing the first down leaves the second's member running and its Job Object handle usable, with the first's leftover report reflecting only its own job. On POSIX, a launch whose direct child has been reaped, and whose identifier equals the process group of another live launch, leaves that group's members running through every teardown operation, and its leftover report comes only from membership checks made before its direct child was reaped

### 17.3 Issue Tracker Client

- Candidate issue fetch uses active states and project identifier
- An empty active list returns no issue and sends no request on every tracker kind, and no adapter substitutes a built-in state list
- On a tracker that derives state from labels, an open issue with no configured state label is not a candidate and is counted as skipped, a closed issue reads terminal whatever its labels, a terminal label outranks a handoff label, which outranks an active label, and a state list changed by a reload applies to the next operation, a cached `304 Not Modified` response included
- On a tracker that derives state from labels, `transition_issue` adds the target label before any removal, closes last for a terminal target, refuses a handoff target on a closed issue with nothing written, writes only the target label and labels naming configured states, leaves labels of exactly one configured state on success, and leaves the start state or the target when any step fails; on GitLab the native status change is a request of its own
- Adapter contract tests cover: normalized field mapping, pagination order, error categories
- Each tracker adapter ships its own integration test suite
- Empty `fetch_issues_by_states([])` returns empty without API call
- Pagination preserves order across multiple pages
- Labels are normalized to lowercase
- Issue state refresh by ID returns minimal normalized issues
- Error mapping covers transport errors, auth errors, API errors, and malformed payloads
- `query_filter` is appended to candidate fetch JQL when non-empty
- `query_filter` is appended to terminal-state fetch JQL when non-empty
- `query_filter` is NOT appended to state-refresh-by-IDs JQL
- Empty `query_filter` produces the same JQL as before (no trailing AND)
- `query_filter` containing OR operators is wrapped in parentheses
- SQLite persistence layer correctly saves and restores retry entries across simulated restart
- Startup recovery from SQLite reconstructs retry timers with correct remaining delays
- Run history is queryable after session completion
- Each tracker adapter's suite exercises the shared tracker conformance assertions: normalized issue shape, ascending comment order, an empty-but-non-nil result on an empty list operation, a state map that omits an unknown id, no request issued on empty input, tracker error kind mapping for every class the adapter can produce, an additive label write, the visibility of an added and of a removed label to the next fetch of the issue and to the candidate listing (`AssertLabelVisible`), the no-write disposition of a removal of an absent label, a candidate's blocker fields agreeing with the adapter's declared blocker source (`AssertCandidateBlockerSource`), a resolved blocker list's normalization (`AssertBlockerRefsNormalized`), and a blocker ref's identifier shape matching the issue's own (`AssertBlockerIdentifiersMatchIssue`)

### 17.4 Orchestrator Dispatch, Reconciliation, and Retry

- Dispatch sort order is priority then oldest creation time
- Dispatch stage labels: an issue that carries a rule's stage label is selected by that rule ahead of every ordered rule, a catch-all and a `labels` match included; an issue that carries none routes as it does without stage labels and never matches a rule with a stage label; an issue that carries several resolves to the rule listed first and logs one warning naming every label in list order, once per evaluation on the poll tick and on a retry routed afresh, and none for a retry whose selection stands; selection, the duplicate check, and the collision check share one case-insensitive comparison; each load-time stage error reports its field and message, in the order the checks run when a rule has several faults; a catch-all may precede rules with a stage label; `sortie validate` reports every stage label collision with a tracker state, an escalation label, or the parking label, one entry for each rule and collision, and exits with code 1
- Issue with non-terminal blockers in a non-running active state is not eligible
- An issue whose blockers could not be resolved is not eligible either
- Issue with terminal blockers is eligible
- Active-state issue refresh updates running entry state
- A named non-active state stops running agent without workspace cleanup
- A reading of no state keeps the running agent and changes no snapshot or retry on its first consecutive reading and stops it without workspace cleanup on the second, a reading in a configured state between the two clears the first, and a run that ends before the second reading takes the exit disposition of its last configured state
- Retry handling reschedules an issue that reads no state at the same attempt, keeping its session, continuation context, and reaction kind, releases the claim and deletes the retry entry on the second consecutive reading, and never resets the issue's hop record
- An empty per-turn state refresh does not end the turn loop and leaves the last state read as the exit's observed state
- Terminal state stops running agent and cleans workspace
- Reconciliation with no running issues is a no-op
- An issue reported terminal releases its pending reaction entries, reaction attempt counters, pending retry, and claim, whether or not it has a running worker, leaving fingerprint rows intact
- A failed tracker state refresh keeps workers running and releases nothing
- Normal worker exit with the issue still active and no handoff state configured schedules a short continuation retry (attempt 1)
- Normal worker exit with a handoff state configured, the issue still active, and a run on a rule without `next` performs the handoff transition and releases the claim without scheduling a continuation retry
- Handoff transition failure schedules a continuation retry on a non-soft-stop exit and releases the claim on a soft-stop exit
- A successful run on a rule with `next` adds the target rule's stage label, removes the source stage label the dispatch read showed, makes no `TransitionIssue` call, leaves no retry entry, pending reaction, or claim, keeps the issue active, records the target rule and `advanced` on the run's own row, and publishes `stage.advanced` with the hop count after the hop beside the events a normal exit publishes with no retry pending; the next tick dispatches the target rule on a new dispatch with no resume session, and the target's final run takes the handoff transition and ends the hop count
- A workflow with no `next` makes the same tracker calls, persists the same rows apart from the new columns, publishes the same events, and renders an empty `stage`
- A failed label add records the target rule and `failed` on the run's row, publishes `stage.not_advanced` with reason `failed` before the handoff write, falls back to the handoff write with the target the exit would have used, and leaves the hop record unchanged; the warning names each stage label the dispatch read showed and a fresh read lacks, including one a refused single-select add removed
- A hop count at the ceiling sends no label add, records the target rule and `ceiling` on the run's row, publishes `stage.not_advanced` with reason `ceiling` and the unchanged count before the handoff write, takes the handoff write, and logs the count, the ceiling, and the chain path; the write's success ends the hop count
- A failed removal of a source stage label after a successful add keeps the hop (record written, claim released), records `partial` on the run's row, publishes `stage.advanced`, logs the labels left, and the next dispatch selects the target through the hop route
- A made hop cancels every pending reaction kind and a queued retry incumbent and seeds none; the test fails under a build that skips the release or the seeding gate, shown by mutated copies of the code run against it
- After a hop, a listing without the target label dispatches nothing before a direct read; a read showing the label dispatches the target; a read showing neither releases the hold and routes by the read's labels; a failed read holds the issue for that tick; a read showing no state holds the issue for that tick and leaves the record; a terminal or named non-active read ends the hop count; the hold survives a restart
- Each reset trigger (handoff write, terminal exit, non-active exit, park, unpark, reconciliation of a terminal or non-active issue, retry handling of a terminal or non-active issue, the hold's direct read) deletes the hop record and logs the reset; a no-state reading resets the record only on its second consecutive reading by reconciliation, and never through retry handling or the hold's direct read; a stage label moved while the issue stays active does not reset, and a cycle built by moving labels stops at the ceiling, also across a restart
- Reconciliation reads every issue that holds a hop record, whether or not it runs, and a record whose issue is missing from the response is kept with its no-state flag unchanged
- Two hop writes from one source dispatch count once; the record write deletes the issue's retry row in the same transaction and leaves other issues' rows; a hop record, a retry row, and a run-history row round-trip their stage fields and chain identifier across a restart; a result update lands on the row of the given id only, and a missing id is a no-op
- A hop record round-trips the issue's type and state as the hopping run read them and its labels as the hop leaves them, which are the run's read without the stage labels the hop removes and with the stage label it adds; an empty list and an unread one stay distinct across a restart
- Routing: of several staged candidates on one chain the most downstream is selected, of candidates on separate chains the lowest list index among the most downstream, the hop target is selected ahead of a downstream leftover label, and with no `next` anywhere selection equals list order
- A retry that keeps its frozen rule, a persisted retry after a restart, a reaction continuation, and a pending reaction recovered at startup render the frozen `stage.previous` pair; a retry routed afresh renders as a poll tick; every site that copies the rule name onto a retry, reaction, or persisted row copies the pair and the chain identifier too
- Chain inheritance: a poll-tick dispatch no hop reached gets a fresh non-empty chain identifier that differs from earlier rows and from the dispatch ID, a dispatch a hop reached inherits the hop record's chain, a retry that keeps its rule, a persisted retry after a restart, a reaction continuation, and a pending reaction recovered at startup carry the chain of the run they continue, a retry routed afresh resolves its chain as a poll tick does, and an empty carried chain is replaced by a fresh one; in a two-stage chain both rows share one chain identifier
- A reload that removes the run's rule, its `next`, the target rule, or the target's `stage` records empty decision fields, routes no stage event, and logs no hop warning; an exit whose row append failed makes no result update and still routes the stage event
- Stage events are opt-in: an entry that lists `stage.advanced` receives it and an entry that does not list it does not, and with a tracker configured and no `tracker_comment` entry neither stage event reaches `tracker_comment`
- A stage event's webhook body carries `stage` with the decision's values, and `reason` on `stage.not_advanced` only; every other event's body is byte-identical to a body without a stage transition
- `sortie stats` lists one `by_chain` entry per chain with a hop-involved row, with that chain's runs, stages, and last hop and the figures `by_rule` computes over the same rows; rows without a chain and chains without a hop-involved row are absent, and the text form prints at most 20 entries and one note naming the total
- `chain_funnels` lists one funnel per stage chain definition: one chain, two entries into one shared stage, and a two-stage branch that joins mid-chain give the stage order, `entry`, and `last` of the definition, and chains that share no stage give separate funnels
- On a chain of three stages whose passes and live passes cover every outcome and every arrival, each stage's `entered` equals the sum of its `arrivals` and the sum of its `outcomes`, `outcomes.no_hop` equals the sum of its `no_hop_reasons` passes, `advanced` is `0` on the last stage and `handed_off` is `0` elsewhere, and the latest deciding run decides a pass; a run that ended with a `blocked` soft stop reads as `no_hop` with `needs_person` on the last stage, never as `handed_off`
- A funnel stage's `runs` equals the `runs` of the `by_rule` group of its rule while a reaction run and a run without a chain identifier are among the rows; a reaction run without a hop result changes nothing but `runs`, and one with a hop result decides its pass
- A pass that a live pass and finished runs both supply counts once: as `in_stage`, or, for a budget hold, as `no_hop` with `budget_held` when its latest run made no hop decision and as `handed_off` after a handoff on the last stage; a pass only a live pass supplies counts once, with the arrival its previous rule gives and no median sample; with `until` before `generated_at` live passes change nothing
- On a database without the `agent_blocked` column, the scan succeeds and `chain_funnels` is `[]`, with the funnel warning while stage chains exist and without it otherwise
- The run a `blocked` soft stop records carries `agent_blocked`, and the run of a handoff exit does not
- A dispatch without a reaction kind, from the poll tick and from the retry handler, leaves the issue's `running` row in `live_passes`, and a reaction dispatch leaves none; any worker exit leaves no `running` row; a budget refusal in the retry handler leaves the retry's `budget` row; a rebuild of budget holds leaves a `budget` row for each hold and none for a hold that ended; startup empties the table
- `sortie stats --format json` on a workflow with a chain of three stages and a database whose passes advance, stop at the ceiling, fail a hop, and are held by a queued retry, a `running` row, and a `budget` row serves one funnel whose `entered` equals both sums on every stage, with the queued and running passes `in_stage` and the held one `budget_held`; the same database under a workflow without stage chains serves `chain_funnels` `[]`
- The migration adding the stage chain columns, on a database holding rows in `run_history`, `retry_entries`, and `stage_hops` keeps every row unchanged with `''` in the new columns
- The migration adding `first_after_hop`, on a database without it, sets it on the earliest run of each hop and on no later run
- The migration adding `agent_blocked`, on a database holding rows in `run_history`, keeps every row with `0` in it and creates `live_passes` empty
- Normal worker exit whose freshest observation is terminal suppresses the handoff transition, the continuation retry, and every reaction enqueue, from each of the three observation sources (reconciliation, the worker's own refresh, and the dispatch-time snapshot)
- With terminal states configured and a non-terminal observation, one verification read runs immediately before the handoff write; a terminal result suppresses the write and a failed read lets it proceed
- With a withheld handoff-evidence verdict, terminal states configured, and a tracker adapter present, one verification read runs before any withheld-handoff effect; a terminal result routes the exit to the terminal disposition, and a non-terminal result, a response omitting the issue, or a failed read keeps the withheld disposition
- With no terminal states configured, no verification read is issued
- A blocked soft stop releases the claim with no handoff and no continuation retry, and, where the dispatch drives issue state, records a durable park, applies the parking label, and holds the issue out of dispatch (§14.2)
- A blocked soft stop from a dispatch that does not drive issue state records no park
- `ShouldDispatch` and the dispatch loop's pre-built-set variant return false for a parked issue regardless of the configured effort budgets
- A retry timer firing for an already-parked issue releases the claim and deletes the retry row without dispatching, under every evidence policy, and this refusal does not disturb the retry lane's own ability to park a newly ceiling-exhausted issue
- The release rule: a tracker state change unparks the issue; a confirmed parking label observed absent unparks the issue; an unconfirmed label observed absent leaves the park in place; a parking label observed while unconfirmed is recorded as confirmed
- A failed parking-label write leaves the park in place with the label unconfirmed, and a later release pass that still observes the label absent does not unpark the issue on that evidence alone
- A successful parking-label write does not by itself confirm the label; only a later observation of the label on the issue does
- Loading persisted park records at startup restores the runtime park set, with each park's run (rule, stage lineage with its pass dispatch time, agent kind, and model), title, link, type, and labels, so the parked row after a restart equals the row before it, skipping a malformed record and loading a record with no recorded tracker state
- The runtime snapshot reports the parked-issue count and the parked list always, the list empty when no issue is parked, and no reason map
- A parked issue absent from the poll tick's candidate set is read for its state through a separate, filter-free tracker call, and that call carries only the parked issues the candidate fetch did not return
- A park that holds no read of its issue takes the candidate's read or, when the candidates omit the issue and the state read finds it, one single-issue read, and is never read for it again; a park released on that tick is neither read nor written, and a failed single-issue read leaves the park as it was and is tried again on the next tick
- A park that holds a title or link and no labels takes the candidate's type and labels without the candidate's copy of the parking label, keeps its title and link, and adds no tracker call
- A poll tick that parks an issue for consecutive absences records the park with the dispatch rule, stage lineage, agent kind, and model of the issue's newest agent run, read in one store call; when that read fails the tick still parks the issue, without a run, and logs one warning
- Parking on the consecutive handoff-absence ceiling and parking on a blocked soft stop produce the same durable record shape, differing only in the reason attributed to the park
- Releasing a park resets its consecutive-absence count whatever reason the park carries; for a released absence-ceiling park, the same poll tick does not immediately re-derive the exhausted count and park the issue again
- A park held under `tracker.handoff_evidence: off` is not released by the policy, and no new absence park is taken while the policy is set
- A retry-lane absence park records no observed tracker state; the next poll tick backfills it without releasing the park, and a state change observed after the backfill releases it
- A worker exit whose own run is parked for absence and later reports a work-observed verdict releases the park
- One park produces exactly one park log record and one park counter increment, whichever trigger produced it
- The worker-exit absence park records the same tracker state the run's own terminal observation resolved, not an unrecorded state, and is releasable by a later state change without an intervening backfill tick
- The consecutive-absence ceiling reads only `agent.max_consecutive_absences` on every lane that evaluates it, including shutdown drain: its value does not move when `agent.max_sessions` moves, and a worker exit processed during shutdown drain resolves the same ceiling a worker exit processed by the ordinary event loop would
- An issue entering the per-issue budget-exhausted set, on either the poll tick's rebuild or the retry lane, produces exactly one log record naming the issue, the reason, the used and budgeted numbers, and, where the fired ceiling's governing setting is known, the setting itself
- The record and its counter increment fire once per hold: repeated ticks over the same held issue produce neither, and an issue that leaves the candidate set and returns still held under the same reason produces neither either
- A park carrying a ceiling also names the setting behind it; an `agent_blocked` park, which carries no ceiling, names neither
- Whichever lane, poll tick or retry timer, discovers a hold is the only one that announces it; the other lane's rebuild or block leaves the announcement memory alone
- The budget-exhausted gauge reports a per-reason level derived from the current set, seeded to zero for every declared reason on each recompute, so a reason that clears reports zero rather than freezing at its last published value
- Both `GET /api/v1/state` and `GET /api/v1/{identifier}` carry the budget-exhausted record's identifier, reason, and numbers, and the per-issue endpoint answers for a budget-blocked issue instead of reporting it unknown
- Retry rows of both endpoints carry the trigger, the reaction kind with its `reactions` key, and the paused flag, and a retry the retry timer rescheduled carries its reschedule reason instead of the error of the run before it; both endpoints serve a parked issue, the per-issue one instead of reporting it unknown
- Both endpoints carry one pending reaction row per issue and kind, with the `reactions` key the kind is configured under, the pull request with its link, the creation time, the next check time, the wait reason, the tries used of the kind's ceiling, the escalation time and, while one stands, its trigger, and the latest check result; `counts.pending_reactions` equals the list length, and the list is empty when no reaction is pending
- A pending reaction row serves `null` for a `merge-conflict` mergeability the provider has not computed, `null` tries and ceiling and no wait reason for a `label-review` row, and a `null` escalation time and no escalation trigger until the reaction escalates
- A pending reaction row serves the pull request link the provider reported, the reason of the pass that last returned the entry (poll interval, debounce, backoff, retry slot, or triage), and a next check time equal to the entry's retry time; a debounced review row's next check ends the debounce window and its actionable and new comment counts equal the comments served
- The per-issue endpoint answers 200 with status `pending_reactions` and the issue's rows for an issue held only by a pending reaction, keeps every other status for an issue that already resolved, and answers 404 for an identifier in no list
- A registered secret held in a pending reaction's branch, link, or failing check name is masked in the row
- A registered secret held in the issue type, a label, or the state of a parked, pending reaction, or between-stages row is masked in the row

### 17.8 Real Integration Profile (Recommended)

These checks are recommended for production readiness and may be skipped in CI when credentials, network access, or external service permissions are unavailable.

- A real tracker smoke test can be run with valid credentials supplied by the appropriate tracker credential environment variable or a documented local bootstrap mechanism.
- Real integration tests should use isolated test identifiers/workspaces and clean up tracker artifacts when practical.
- A skipped real-integration test should be reported as skipped, not silently treated as passed.
- If a real-integration profile is explicitly enabled in CI or release validation, failures should fail that job.
- NITE (Nightly Incident Triage Engine) applies a consecutive-sample stability policy to each shard's real-integration run: a configurable number of consecutive failing samples opens or reopens one durable incident per shard, and a configurable number of consecutive passing samples closes it, rather than a single failing or passing sample changing the incident's state by itself.
- Each agent adapter runs as a scripted shard and a live shard, each with its own incident. The scripted shard runs the scripted-model case on every scheduled run. The live shard runs the adapter's other gated cases at a lower cadence, one that keeps the previous live sample inside the run history the incident policy reads even when a single live run is missing. A manual run executes both. A runtime with no scripted case has only a live shard. A live shard whose credential variable is empty fails as a setup failure instead of passing with every case skipped.
- Nightly summaries report the tested version, test counts without duplicate parent results, skipped-test reasons, and bounded failure evidence even when no incident action is selected; summaries are also printed to the job log and retained with the decision JSON as per-shard artifacts. A passing parent whose children all skipped does not establish execution. A parent that skips after running children retains its own skip reason and makes coverage partial.
- Nightly classification distinguishes test/package failure from setup failure without claiming a diagnosed adapter-contract violation. Coverage reports complete, partial, or no execution independently of the incident policy; prior-run evidence remains limited to GitHub job conclusions, and a prior job whose conclusion carries no verdict (skipped or cancelled) is passed over rather than taken as the prior sample.
- Each Codex nightly shard enables the Linux user namespaces its sandbox requires on its disposable runner and probes the installed sandbox before running integration tests; a failed probe is reported as setup failure. The runtime's workspace sandbox remains enabled.
- A shard's own job still fails on its first failing sample regardless of the incident's state; the stability policy governs only the durable incident, never the shard's pass/fail conclusion.
- A degraded read of the incident listing or of the prior-sample history downgrades an incident-opening, reopening, or closing action and raises a visible error annotation for an executed sample even below the incident threshold, rather than silently filing nothing or asserting a recovery the read could not confirm.

### 17.9 Source-control Adapter and CI Provider Roles (Core Conformance)

- Each source-control adapter's suite exercises the shared source-control conformance assertions: an empty-but-non-nil result on each list method with no results, source-control error kind mapping for the auth, not-found, payload, and API classes, the already-merged marker on a merge that raced an external merge, the absent-branch disposition on a delete of a missing branch, the absent-label disposition on a removal of an absent label, a correctly ordered label-event journal, a label-event entry whose timestamp does not parse failing the read with the payload error kind and yielding no events, and a review comment whose timestamp does not parse not failing the read and carrying the zero timestamp. A forge whose review decision is folded from per-review submission times fails that read on an unparseable timestamp of a review that can change the verdict, an adapter-specific obligation with no shared assertion. A forge whose review-comment route reports the two diff sides as separate line fields returns each comment with the line of the side it is anchored to and marks no comment outdated, an adapter-specific obligation with no shared assertion.
- Each CI provider's suite exercises the shared CI-aggregate conformance assertion against a result containing at least one completed-failing run, one in-progress run, and one completed-success run, confirming the provider's aggregate status and failing count agree with the forge decision core.
