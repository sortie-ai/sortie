# Add or refresh an agent adapter

This guide is the ordered procedure for adding a runtime to Sortie's agent adapters, whether by writing a new Go package or by adding a runtime to the generic Agent Client Protocol kind, and for keeping a runtime's support current afterward: qualifying it, refreshing it once its upstream changes, and moving it from a native kind onto the protocol when that is warranted. It assumes the mental model in [Agent adapter architecture: concepts](agent-adapter-concepts.md); read that first if a step below does not make sense on its own.

## Add a new agent adapter kind

This section writes a new Go package under `internal/agent`, for a runtime that does not already reach Sortie through the generic `agent-client-protocol` kind. A runtime that kind can already drive needs no new package at all: skip to [Add a new runtime through the Agent Client Protocol](#add-a-new-runtime-through-the-agent-client-protocol) instead.

1. **Create the package.** Add `internal/agent/<name>`, one package per kind. Give it a package comment naming the external system and the `domain.AgentAdapter` interface it implements, per the project's Go documentation conventions.

2. **Implement `domain.AgentAdapter`.** Implement `StartSession`, `RunTurn`, and `StopSession` against `domain.Session`, `domain.StartSessionParams`, `domain.RunTurnParams`, and `domain.TurnResult`. The constructor takes no arguments and the adapter type holds no setting. Read every setting from `StartSessionParams.Settings` in `StartSession`, before anything launches, and keep what you parsed in the session's own state for `RunTurn` and `StopSession`. Report a block you cannot parse with `agentcore.SettingsError`, which returns an `agent_not_found` error wrapping the fault and carrying the text your `ValidateAgentConfig` reports for it. Read `model` through `registry.ModelSetting` and `effort` through `registry.EffortSetting`, and deliver both on every turn, the first turn of a resumed session included. Parse the runtime's actual wire format inside this package only, and normalize every result to `domain.AgentEvent`, `domain.TurnResult`, and `domain.AgentError` before returning it. Add a compile-time assertion, `var _ domain.AgentAdapter = (*YourAdapter)(nil)`, next to the type definition.

3. **Handle a credential-verification session.** The shared step (`agentcore.VerifyCredential`) drives `StartSession`/`RunTurn`/`StopSession` with `StartSessionParams.CredentialVerification` set, before a working session whenever the orchestrator holds no fresh proof of the same agent setup. On that flag: deliver no tool server, request no continuation, and leave no stored conversation the runtime offers a way to avoid or delete. Declare `AgentMeta.VerificationContext` (step 5) naming the context components the request keeps, and drop every other one with a switch that qualifies: it applies to one launch, persists nothing past the session, cannot change the credential, model, provider, or endpoint, and appears in the runtime's own help text, configuration reference, or published schema. Spell each such switch behind `StartSessionParams.ReducedVerificationContext()`, not behind `CredentialVerification` alone, so the retry under `VerificationFullContext` applies none of them, hand a runtime that can replace its system prompt `agentcore.VerificationSystemPrompt`, and do not pass a kind setting whose only effect is prompt text or tool visibility. Map the runtime's own structured refusal, at session start and on a working turn, to `agentcore.CredentialRefusedError` or, where the turn reports through `agentcore.TurnEvidence`, to `TerminalErrorKind = domain.ErrCredentialUnverified` with `TerminalMessage = agentcore.CredentialRefusedMessage(text)`; build any auxiliary launch (a deletion, a listing, a presence guard) through `LaunchTarget.AuxiliaryCommand`, bounded by `agentcore.AuxiliaryTimeout`; and report a remote connection failure with `sshutil.ErrConnectionFailed` per `sshutil.ConnectionFailed`, the same way a working turn does. Set `fakemodel.Binding.UserInstructions` to the runtime's user-level instruction file, relative to the scenario home, when the declaration does not keep user instructions. Call `credentialtest.AssertCredentialVerification` from the adapter's own test suite (step 7).

4. **Reuse shared helpers instead of writing your own.** Check `internal/agent/agentcore` (session, event, and disposition helpers, including binary resolution via `agentcore.ResolveBinary`, and `agentcore.ResolveToolDelivery` with `agentcore.ToolSession`, which choose the servers a launch receives, deliver Sortie's tool server, and declare a gap in it on every launch), `internal/agent/procutil` (subprocess group handling, graceful shutdown, Windows process containment, and bounded output capture for auxiliary launches), `internal/agent/mcpconfig` (every tool-server configuration dialect, rendered from one server model into an `mcpconfig.Delivery`), `internal/agent/toolrelay` (the host-side relay that serves Sortie's tool server over HTTP for a remote session and for a local protocol runtime), `internal/agent/sshutil` (SSH invocation), `internal/agent/jsonrpc` (newline-delimited JSON-RPC framing and non-blocking message delivery, for a persistent-session protocol), and `internal/agent/agenttest` (shared conformance assertions every adapter's own tests call, including `agenttest.AssertMCPInjection` and `agenttest.AssertUsageReporting`) and its `credentialtest` subpackage (`credentialtest.AssertCredentialVerification`, the shared credential-verification assertion) before writing an equivalent. A runtime that reports a figure cumulative over its own session declares its live source `usage.SpendSessionCumulative`, with the replay rule it follows when the session resumes (`usage.ReplayLastFigure` when it repeats its last figure once, `usage.ReplayNone` when it repeats nothing, in which case the usage component starts a resumed session from the total of the records its records source holds), and the usage component excludes the resumed history, so the adapter subtracts no baseline. A live reading may carry each served model's running total in `usage.SpendReading.ByModel`, and the component then splits the turn per model. A kind that runs one process per turn starts from `agentcore.NewForkPerTurnSession`, which owns the launch, the output reading, the reap, the stop, the ending order, and the turn logger, and keeps only its own argument vector, line parsing, usage source, and environment content. It reaches the rest through the optional `agentcore.ForkPerTurnHooks` members: `PromptOnStdin` for a runtime that reads its prompt from standard input, `FirstEventTimeout` for a deadline on the first accepted line, `SettleUsage` for usage read after the process exits on every ending, `TurnEnv` for the process's environment and an SSH launch's settings, `Tools` and `ToolPlacement` for the `agentcore.ToolSession` that delivers Sortie's tool server and the placement of its finished `mcpconfig.Delivery` on a remote launch, and `agentcore.EndTurn` returned from `ParseLine` to end a turn from its output. A kind declares its dialect in `registry.AgentMeta.MCPDialect`, or `registry.MCPDialectNone` with `MCPDialectNoneReason`, and places the `mcpconfig.Delivery` that `agentcore.ToolSession` hands it, never reading the declared servers itself; a contract test fails an adapter that does. A capability the skeleton lacks is added to it as a new hook in the same change, never copied into the adapter; a contract test fails a package that starts its own streaming subprocess. A helper this task needs that does not exist yet belongs in a new package named for the concern it serves, not folded into `internal/domain` or duplicated per adapter.

5. **Register the kind in `init()`.** Call `registry.Agents.RegisterWithMeta` with the adapter's kind string and constructor. Every registered kind declares its credential variables, its verification context, and its usage-limit recognition, so this is the registration form a new adapter uses; the bare `Register` carries no `UsageSources`, which panics at registration, and leaves `CredentialEnv`, `VerificationContext`, and `UsageLimitRecognition` undeclared, which fails the completeness checks in step 8:

   ```go
   func init() {
       registry.Agents.RegisterWithMeta("your-kind", NewYourAdapter, registry.AgentMeta{
           RequiresCommand:     true,
           ValidateAgentConfig: validateConfig,
           MCPDialect:          registry.MCPDialectMCPServersJSON, // or another dialect, or MCPDialectNone with MCPDialectNoneReason
           UsageSources:        yourUsageSources, // a package-level usage.Sources value, declared beside the parser
           CredentialEnv:       registry.DeclareCredentialEnv("YOUR_API_KEY"),
           EffortForwarding:    registry.EffortForwarded, // or NotForwarded
           VerificationContext: registry.DeclareVerificationContext(), // keeps nothing; name each kept component
           UsageLimitRecognition: registry.UsageLimitRecognized, // or UsageLimitNotRecognized with UsageLimitNotRecognizedReason
       })
   }
   ```

   `CredentialEnv` names the environment variables this kind's runtime reads as the credential for its default provider, in the order a remote launch carries them. A kind whose runtime reads none says so explicitly with `registry.DeclareCredentialEnv()` and no arguments, which is a different thing from leaving the field unset. Each name must be a valid environment variable name, must not repeat, and must not be one the SSH carrier reserves for itself.

   `VerificationContext` declares which context components the kind's credential-verification request still carries because its runtime offers no qualifying switch that drops them: `registry.VerificationKeepsSomeTools` or `registry.VerificationKeepsAllTools` (at most one), `registry.VerificationKeepsProjectInstructions`, `registry.VerificationKeepsUserInstructions`, and `registry.VerificationKeepsSystemPrompt`. `registry.DeclareVerificationContext()` with no arguments declares a request that keeps nothing, which is a different thing from leaving the field unset. A completeness test in `cmd/sortie` fails, naming the kind, when a registered kind leaves it unset, and `fakemodel.AssertConformance` proves on the wire that every component the declaration does not keep is absent from the verification request.

   `UsageLimitRecognition` declares whether the adapter returns `domain.ErrUsageLimit` when its runtime refuses a request because the account's usage limit is reached. Declare `registry.UsageLimitRecognized` only for an adapter that reads a structured field of the runtime's output, never message text, and reports the instant the allowance reopens in `domain.UsageLimit.ResetsAt` when the runtime gives one, and `ModelOnly` when the exhausted allowance covers one model only. The adapter passes the fact to `agentcore.FinalizeTurn` through the turn evidence. Declare `registry.UsageLimitNotRecognized` with `UsageLimitNotRecognizedReason` stating why the adapter cannot; the reason is required with that value and empty otherwise. A completeness test in `cmd/sortie` fails, naming the kind, when a recognizing kind that launches a command has no test calling `agenttest.AssertUsageLimitRefusal`, which replays a recorded refusal from the runtime and asserts the normalized outcome.

   `EffortForwarding` declares what the adapter does with the `effort` key of its own settings block. Declare `registry.EffortForwarded` only for an adapter that reads the key through `registry.EffortSetting` from the session's settings and delivers a non-empty value to its runtime on every turn of every session, credential verification and a resumed session's first turn included; such a kind's tests call `agenttest.AssertEffortForwarding`, and a completeness test in `cmd/sortie` fails, naming the kind, when they do not. Declare `registry.EffortNotForwarded` for an adapter that reads no such key, and leave `registry.EffortSetting` and `registry.EffortKey` out of its non-test files. An adapter whose runtime lets an environment variable outrank the delivered level sets `LaunchTarget.WithheldEnv` to that variable's name in `StartSession`, right after `agentcore.ResolveLaunchTarget` returns, when the level is set.

   `UsageSources` is a `usage.Sources` value declared beside the parser that reads the runtime's reports. `Live` is required: the runtime's own output (`usage.SourceOutput`) or its protocol messages (`usage.SourceProtocol`), with `usage.StrategyLive`, declaring either the token counts it reports in `Spend` or, when it reports no token counts, the plural name of its unit in `Spend.VendorUnit`. `Records` is optional: the runtime's session records on its host, `usage.SourceJournal` with `usage.StrategyRecords`, and it must count tokens. Registration panics during `init`, naming the kind and the defect, when the live source is missing or reports no spend, or when the records source counts no tokens, and no reason takes the place of a live source. The usage arrival and attribution the orchestrator reads are derived from these sources, so a kind declares neither and no passthrough setting or launch mode changes them. Set `MCPDialect` and `UsageSources` to what the adapter actually does today, not what the underlying CLI could in principle support. Derive the sources from the adapter's own emission code, not from the CLI's documentation: re-read the symbol that decides when a `token_usage` event fires and whether it carries a model before writing the literal. Add `SessionResumeBlockedBy` only if some config key of this adapter's own can block session resume under a given passthrough.

   A kind whose sources derive `UsageArrivalTurnEnd` constructs one `agentcore.TurnEndUsage` per session, directly in `StartSession` rather than in a closure declared there, finalizes every turn through its `Finalize`, and names neither `domain.EventTokenUsage` nor `agentcore.FinalizeTurn` in its own package; the usage contract test in `internal/agent/agentcore` enforces this.

6. **Blank-import the package from `cmd/sortie`.** Add `_ "github.com/sortie-ai/sortie/internal/agent/<name>"` to the import block in `cmd/sortie/main.go`, alongside the existing kind packages. This is the only place a kind package is imported outside its own tests; nothing else needs to change to make the kind resolvable through `registry.Agents.Get`.

7. **Add an env-gated integration test.** Gate the adapter's live-runtime test behind `SORTIE_<ADAPTER>_TEST=1`, one gate for the whole package. Skip cleanly, with `t.Skip` and a message naming the variable, when it is unset or not `1`. Do not add a second gate for a specific operation inside the same package. Run the shared conformance helpers against the adapter's own event stream: `agenttest.AssertMCPInjection`, `agenttest.AssertUsageContract`, `agenttest.AssertMeasurementAbsent` where the adapter reports no token usage, `agenttest.AssertUsageReporting` for the adapter's own usage disposition, `agenttest.AssertUsageLimitRefusal` for a recognizing kind that launches a command, `credentialtest.AssertCredentialVerification` for the shared credential-verification step, `credentialtest.VerifyLiveUsage` on the working-credential case so its verification turn's usage is asserted, and `fakemodel.AssertConformance` with the kind's binding, which runs the installed runtime against a scripted loopback model endpoint (`TestIntegration_ScriptedModel`, under the same gate), runs its SSH variant against a throwaway Docker sshd container, which needs `docker` on `PATH` and otherwise skips with a reason naming it, and, in a session of its own, has the scripted model call `sortie_status` on the real Sortie tool server. That call passes only when the relay process that answered it holds the `SORTIE_DISPATCH_ID` and `SORTIE_WORKSPACE` the MCP config's `env` block declares. A binding whose scripted settings let the runtime approve every tool call by itself sets `ToolServerPassthrough` to narrower settings for that session. A binding whose runtime does not offer that tool under its own name, optionally prefixed with the server's, sets `SortieStatus` to the call that reaches it. The driver also runs a session that resumes an earlier one by its reported identifier, so the binding's settings must leave the runtime able to resume a session it stored. A completeness test in `cmd/sortie` fails, naming the kind, when a kind requiring an agent command has no test calling `fakemodel.AssertConformance`. A kind whose MCP dialect delivers tools also sets `SSH` on its binding: `Package` and `HostCommand` for a runtime published on npm, which the lab installs at the version the host runtime reports, `Install` for any other install script, or `Skip` with the reason the variant cannot run. The same completeness test fails, naming the kind, when the binding leaves `SSH` unset. The SSH variant's forwarding-allowed run also checks usage against whether the kind's sources can carry a token figure on that launch: a kind that can must report a figure equal to everything the endpoint served, and a kind that cannot must report the run unmeasured. A binding sets `Spend` from its runtime's source declarations, naming the source category and strategy of its live source and of its records source, and sets `Spend.LowerBound` when the figure its live source settles is a lower bound. A completeness test in `cmd/sortie` fails, naming the kind, when a kind requiring an agent command has a binding without `Spend`. An opted-in binding also runs the kill and, in the SSH variant, the cancellation after output and the continuation, and every turn asserts the exact figure and the provenance the usage component reports. A test that needs a turn the built-in scenarios do not script, such as a tool-forcing turn, drives it with `fakemodel.RunCustomTurn` and a `fakemodel.CustomTurn` carrying its own script and prompt, from any package. `RunCustomTurn` asserts nothing and sets environment variables for the rest of the test, so the caller checks the returned run with `fakemodel.AssertExactUsage` or its own assertions and does not run it in parallel. To probe a remote runtime by hand, `make ssh-lab INSTALL='npm install -g <package>@<version>'` starts the same lab, prints the `ssh` command that connects, and keeps the container running until interrupted; `make ssh-lab-clean` removes every lab container and image afterward.

8. **Run the contract tests.** `make test` runs `go test -race ./...`, which includes `internal/adaptertest`. Its checks catch a cross-adapter import, an orchestrator import of the new package, a vendor name leaking outside the new package's own directory (rule IDENTITY), and a duplicated helper the ban table already names an owner for. Fix a violation there before moving on; it is enforced independently of whether the code otherwise compiles and runs.

9. **Write the adapter notes file.** Add `docs/<kind>-adapter-notes.md`: the runtime fact everything else follows from, how to recover a volatile detail from the installed binary, and any exit-code or output behavior the adapter works around. Keep it prose the next maintainer reads before touching the code, not a log of what changed and when.

## Add a new runtime through the Agent Client Protocol

A runtime that speaks the Agent Client Protocol needs no Go package of its own. It reaches Sortie through the existing `agent-client-protocol` kind, configured by `agent.command` like any other kind; what makes it a supported runtime is a tracked profile document and a completed qualification run, not new production code.

1. **Write the runtime's profile document.** Add `tools/qualify/profiles/<runtime-id>.json`, modeled on an existing tracked profile such as `tools/qualify/profiles/gemini-cli.json`. Name the runtime's identity tokens, its future adapter-notes and measurement-artifact paths, the argument vector for each surface the runtime actually exposes (the protocol entry point always; `native_json` or `native_stream_json` too, when the runtime has a structured output mode of its own), how to recognize a terminal outcome on each structured surface, and any capability the runtime cannot produce as a declared gap or declared absent surface. `profile.Decode` rejects an unknown or missing field at any level, so a typo in a key fails the next step immediately rather than silently measuring nothing.

2. **Qualify the runtime for the first time.** Follow [Qualify a runtime for the first time](#qualify-a-runtime-for-the-first-time) against the profile just written. It produces the runtime's `EligibilityReport`, its adapter notes file, and its tracked measurement artifact. Nothing here requires a `qualified` verdict before the runtime counts as supported: a fresh runtime onboarded this way records what the run found, gaps and all, rather than gatekeeping the addition on the outcome.

3. **Point operator configuration at it.** Set `agent.kind: agent-client-protocol` and `agent.command` to the runtime's binary plus the flag or subcommand that puts it into protocol mode (for example `gemini --acp`); see the workflow reference's agent configuration section for the full field semantics. The generic kind itself declares no fixed credential environment variables, because it names no default runtime: whatever the specific binary needs to authenticate is that runtime's own concern, carried the same way any other environment variable reaches the process. The runtime's scripted shard in the nightly run sets `SORTIE_CLIENTPROTOCOL_MODEL_BASE_URL_ENV` to the variable through which it takes its model base address, and `SORTIE_CLIENTPROTOCOL_CREDENTIAL_ENV`, so the scripted cases run against it; it sets the first only for a runtime whose whole redirect is that one variable. The shard sets the scripted coordinates only for a runtime that continues a session it created, through `session/load` or `session/resume`, because the scripted cases resume a session by its identifier; a runtime that cannot continue a session it created gets no scripted cases. A runtime with no scripted cases runs only as a live shard. The scripted shard also sets `SORTIE_CLIENTPROTOCOL_ASKING_COMMAND` to the same runtime's launch command in a posture that asks before running a tool, which makes the scripted refusal case run; without it that case skips. A runtime whose verification request keeps no user instructions also gets `SORTIE_CLIENTPROTOCOL_USER_INSTRUCTIONS`, the path of its user-level instruction file relative to the scenario home, and a runtime that takes its model endpoint from a configuration file rather than a variable gets `SORTIE_CLIENTPROTOCOL_MODEL_DOCUMENT`, a provider document the scripted cases write into the scenario home with `{url}` replaced by the endpoint, its path handed to the variable `SORTIE_CLIENTPROTOCOL_MODEL_BASE_URL_ENV` names. A runtime that reads its endpoint from a file at a fixed place in its home directory gets `SORTIE_CLIENTPROTOCOL_MODEL_DOCUMENT_PATH` instead of that variable, the document's path relative to the scenario home. A runtime whose declaration recognizes a usage-limit refusal and whose scripted model can serve a stand-in refusal also gets `SORTIE_CLIENTPROTOCOL_USAGE_LIMIT_ANSWER`, the path of a JSON document holding one stand-in answer (`status`, `header`, `body`) and the expected `model_only`, which makes the `usage_limit_refusal` case run locally and over SSH; without it that case skips.

4. **Register a verification addition when the runtime can drop agent context.** Session creation in the protocol carries no context member, so a runtime's switches for a credential-verification request enter through the per-runtime seam beside usage declarations. Add a file in `internal/agent/clientprotocol/usagesource` with a type implementing `usagesource.VerificationAddition`, registered from `init` into `usagesource.VerificationAdditions`. `Claim` refuses a remote launch and a command line that does not name the runtime, creates any file its switches name, and returns the environment entries and arguments to add; `Context` declares what the request keeps once they apply; `Close` removes what `Claim` created. A switch qualifies under the rules in step 3 of [Add a new agent adapter kind](#add-a-new-agent-adapter-kind). Give the runtime a nightly row that runs only `^TestIntegration_ScriptedModel$/^credential_verification_context$` against the loopback model, reaching it as the runtime's native binding does: a test in `internal/agent/clientprotocol` fails, naming an addition that drops a component and has no such row. A runtime that cannot be driven against the loopback model declares every component kept, so it claims no saving and needs no row.

5. **Declare the runtime's usage-limit refusal.** The kind recognizes a provider usage-limit refusal per runtime, in the usage declaration the handshake name selects, beside the declaration's spend and window members in `internal/agent/clientprotocol/usagesource`. The transport names no runtime and consults only these members:
   - `PromptError` reads a `session/prompt` error response and returns a verdict: a refusal, or a transient provider failure that must not read as a rejected credential or a refusal. A declaration's verdict outranks the `-32000` credential rule.
   - `TurnNotification` reads a notification of the turn that is neither `session/update` nor `session/request_permission`, for a runtime that reports the refusal as a notification and then ends the turn normally. It can also report that the runtime announced a retry, which stops a later notification of the same turn from counting as a refusal.
   - `InitializeMeta` is the `clientCapabilities._meta` object the `initialize` request carries, for a runtime that sends the notification only to a client that subscribed. It requires `Launches`, so the subscription goes only to a launch whose command names the runtime, locally and over SSH alike.
   - A refusal states `ModelOnly`, true wherever the allowance is per model or not known to cover the account, and `WindowReset`, true when the reset comes from the exhausted windows of the turn-end pull. `WindowModel` maps a pulled window to the one model it meters, so the settings block's `model` scopes the reset; leave it nil when no window meters one model.
   - `ReadRecords` returns the refusal the runtime's own records hold for the turn, with its reset instant, when the protocol error drops the delay the records keep.

   Recognize only members the runtime itself produces, such as an error name, a typed error class, or a notification method, and never message text, a provider's status or body, or a field a stand-in upstream authored. A refusal with no such member stays unrecognized, and the runtime's adapter notes list it. Prove the declaration with `agenttest.AssertUsageLimitRefusal` on `agent-client-protocol`, replaying a recorded refusal of the runtime, and add a negative case for each throttle or capacity error the runtime sends in a similar shape. Keep the capture's provenance: say which frames are the runtime's own and which are the stand-in upstream's.

## Qualify a runtime for the first time

This is the procedure for a runtime that has never been measured: no tracked profile, no adapter notes, no measurement artifact. [Add a new runtime through the Agent Client Protocol](#add-a-new-runtime-through-the-agent-client-protocol) and [Move an existing native adapter onto the protocol](#move-an-existing-native-adapter-onto-the-protocol) both start here once their own profile document exists.

1. **Drive a live capture.** Run `make qualify-live`, which runs `TestQualificationProfile`, the single gated entry point in `tools/qualify/probe`, to collect a fresh set of `evidence.Record` rows, one row per surface-capability-case observation. The gate is `SORTIE_CLIENTPROTOCOL_QUALIFICATION_TEST=1`, the same one-gate-per-package convention an adapter's own integration test uses. Set alongside it are the run's four coordinates, read from environment variables of their own and never printed: `SORTIE_CLIENTPROTOCOL_QUALIFICATION_COMMAND` (the runtime's resolved executable path, no arguments), `SORTIE_CLIENTPROTOCOL_QUALIFICATION_MODEL` (the model identifier applied to every measured surface), `SORTIE_CLIENTPROTOCOL_QUALIFICATION_AUTH_ENV_NAMES` (a comma-separated list of the credential environment variable names the run checks are populated; an empty list declares a stored-login runtime rather than an omitted one), and `SORTIE_CLIENTPROTOCOL_QUALIFICATION_PROFILE` (the profile document to measure against). This target spends provider quota and is opt-in: no automated workflow ever runs it. A misspelled gate name skips the run and reports success, so read the skip line rather than the exit status when a run produces nothing.

2. **Read the report.** A capture can be re-scored without spending anything further: `make qualify-report CAPTURE_DIR=<path> PROFILE=<path>` re-derives the report offline through `eval.Run` and `eval.Render` and only renders it, writing nothing back, needing no runtime, credential, or network for that pass. Read `EligibilityReport.Verdict` and `EligibilityReport.Conformance`, the two fields `eval.ExplainEligibility` returns; the report answers two questions over one row set, and neither answer stands for the other.

   `EligibilityReport.Verdict` answers transport parity: `qualified` only when every load-bearing capability's protocol route grade, counting a usable figure Sortie's own code supplies outside the protocol, meets or beats its richest native reference, `not_qualified` when one falls short, and `unmeasured` when a row this run needed went unobserved. It is the verdict that decides routing, and it says nothing about whether a capability works: a shortfall both routes share satisfies it.

   `EligibilityReport.Conformance` answers product conformance: does the effective adapter meet Sortie's own obligation, counting what Sortie's code supplies outside the protocol and reading no native surface. The token-ceiling row's own evidence for this answer is the live run through Sortie's own orchestrator under a one-token `agent.max_tokens`, satisfied only when the run stopped there and no dispatch followed. A capability neither route delivers is `not_qualified` here while parity reads `qualified`, and that pair is the normal shape of an open product gap rather than a contradiction. Report both; a reader given only one will take it for the other.

3. **Record the measurement artifact.** `make qualify-reemit CAPTURE_DIR=<path> PROFILE=<path>` is the third and last qualification target: it rewrites `measurement.json` inside the capture directory from the run's own evidence and provenance, bound to the profile document's own digest (`RuntimeProfile.Digest`) so a later edit to the profile without a fresh run is detectable rather than silently treated as still current. It carries the run's provenance digest along with it, because a profile digest and a date are shared by two runs of different collector builds and so do not identify which build measured this. Like `qualify-report`, it needs no runtime, credential, or network; unlike `qualify-report`, it writes. Commit the capture directory's `evidence.jsonl`, `measurement.json`, and `provenance.json` into the directory the profile's `measurement_path` points into.

4. **Write the adapter notes file to match.** Add `docs/<kind>-adapter-notes.md` in the present tense, describing current behavior rather than a changelog of what changed. Its required sections, its one `Eligibility:` line carrying the transport-parity verdict, its `Product conformance:` line where the run answered that question, and its per-surface-capability status rows must match the `EligibilityReport` exactly. Do not write a conformance line into a document whose run produced none: `evidence.ValidateNotes` rejects a verdict no measurement stands behind. Validate the document against the run's expectation with `evidence.ValidateNotes` before treating the qualification as done; a mismatched grade row or a missing section is a defect in the notes, not an acceptable rounding of the measurement.

## Refresh an existing adapter after the upstream runtime changed

1. **Re-run the adapter's own integration suite against the new binary.** Set the adapter's `SORTIE_<ADAPTER>_TEST=1` gate and whatever command or credential variables its suite reads, and run it against the updated runtime. A test asserting the shape of what the runtime sends (handshake fields, a terminal event's own member names) is the one class of failure that distinguishes a real behavior change from a fixture that merely still parses; do not treat a pass as clean without that assertion actually exercising the new binary's output.

2. **If the runtime is reached through the generic `agent-client-protocol` kind, re-measure before changing anything.** Update the runtime's tracked profile document under `tools/qualify/profiles/<runtime-id>.json` to reflect the change: an entry point's argument vector, a recognizer's terminal-locating fields, a newly declared gap, or a newly declared absent surface. Then follow [Qualify a runtime for the first time](#qualify-a-runtime-for-the-first-time) against the updated profile, reading the fresh `EligibilityReport` against the one the current adapter notes and measurement artifact describe to see what moved.

3. **Update the adapter notes file to match the fresh measurement.** Same requirement as a first qualification: the document's required sections, its `Eligibility:` line, its `Product conformance:` line where the run answered that question, and its per-surface-capability status rows must match the new `EligibilityReport` exactly, validated with `evidence.ValidateNotes` before treating the refresh as done.

4. **Record the fresh measurement artifact.** Re-emit it the same way a first qualification does, with `make qualify-reemit CAPTURE_DIR=<path> PROFILE=<path>`, and commit the result over the runtime's tracked measurement document.

## Move an existing native adapter onto the protocol

A runtime already reachable through its own native kind is a candidate for this migration once the protocol route has been measured against it. Nothing retires the native kind automatically; this procedure is what decides whether the operator can be pointed at the protocol route without losing anything, and it leaves the native package in place until a maintainer removes it separately.

1. **Qualify the runtime for the first time, if it has no tracked profile yet.** A runtime with only a native adapter today has nothing under `tools/qualify/profiles/`. Write one (see [Add a new runtime through the Agent Client Protocol](#add-a-new-runtime-through-the-agent-client-protocol), step 1) naming both the protocol entry point and the runtime's own native structured surfaces, then follow [Qualify a runtime for the first time](#qualify-a-runtime-for-the-first-time) in full. The reference the report compares against is the runtime's own native surfaces, not Sortie's existing native Go adapter; see [Transport parity and product conformance](agent-adapter-concepts.md#transport-parity-and-product-conformance) for what that reference is and is not.

2. **Read `EligibilityReport.Verdict`, and let only `qualified` authorize the switch.** `qualified` means every load-bearing capability's protocol route grade, counting a usable figure Sortie's own code supplies outside the protocol, meets or beats the richest reference this runtime's own native surfaces can offer, so moving the operator's traffic loses nothing measured. `not_qualified` or `unmeasured` means the runtime stays on its native kind; rerun the qualification after whatever gap it found is closed, rather than switching on a partial result.

3. **Switch operator configuration by hand.** Change `agent.kind` from the native kind to `agent-client-protocol` and set `agent.command` to the entry point the profile measured, per the workflow reference's agent configuration section. Nothing rewrites a `WORKFLOW.md` automatically; each deployment's configuration is edited on its own.

4. **Update the adapter notes file to describe both routes, and add the route-parity record.** Write one document naming which capabilities each route delivers, where they agree, and where a credential or posture setting changes the answer. Keep both `Eligibility:` and `Product conformance:` lines, validated with `evidence.ValidateNotes` against the fresh measurement as usual. Alongside it, add one table to the notes recording the route-parity record the deprecation in the next step rests on: one row per axis the removal condition names, one row per native configuration key graded from a measurement on the protocol entry point rather than from help output, and a row of accepted differences.

5. **Declare `Deprecation` at the native kind's registration once the record shows no withdrawn capability.** Add it to the native kind's own `registry.AgentMeta{...}` registration, naming the protocol kind as `Replacement`; that is what it takes to declare `Deprecation` for a kind. The kind stays registered and every configuration naming it keeps working; `sortie validate` and a run each report the deprecation once through the same advisory mechanism every other configuration advisory uses. Removing the native package once every deployment has moved is a separate, later change, outside this procedure.
